# Agent Note：桌面端首次启动配置与历史迁移

Status: implemented

[English](2026-08-16-desktop-first-run-config-import.md) | 中文

## 问题

桌面启动器需要使用与源码启动隔离的 Harness home，避免两边的服务版本和后续修改相互影响。完全独立的 home 也会让首次安装桌面端时丢失用户已有的提供方、偏好、指令、profile、preset、skill、对话历史和工作区分组，即使桌面端还没有任何需要保留的配置。会话日志不包含工作区注册表的有序归属账本，因此只复制历史后，如果桌面端空注册表已经初始化，所有导入会话都会显示为未分组。

## 决策

使用启动器自有的 `DSH_HOME` 启动服务前，桌面启动器会检查版本化的 `.source-home-import-v1` 标记。完整标记会在 `dsh-home` 存在配置时跳过迁移；配置为空时仍满足迁移条件，因此清空配置会恢复首次启动行为。标记缺失或不完整时，启动器从默认源码 home `~/.dsh` 导入。目标端已有文件始终优先；已有配置目录只接收目标完整路径尚不存在的源码后代。这样，启动器生成的 `profiles` 或 `settings.yaml` 可以与源码端缺失的凭据、profile、preset 和 skill 共存，而不会跳过整次迁移。

`sessions` 和 `attachments` 构成一组历史数据。只有目标端两个目录都不存在时，启动器才会复制源码端可用的目录；目标端任一目录存在，就会保留完整的桌面端历史组合并跳过两个源码目录。成功尝试迁移后，即使没有缺失项，启动器也会原子写入标记，避免源码端后续新增内容变成隐式同步。显式 `DSH_HOME` 会同时绕过启动器自有 home 和迁移。

独立的 `.source-workspace-import-v1` 标记控制工作区分组快照，不受配置和历史标记影响。启动器只接受字段完整、不带待处理变更的 workspace v2 `storages/workspace.json`。目标账本缺失时接收源码账本。经过验证、已初始化且没有工作区和归档会话的桌面端账本不携带用户分组或归档状态，可以由源码账本替换，从而修复源码会话到达前已经初始化的注册表。桌面端非空、不兼容、由符号链接承载或无法识别的账本始终优先。不兼容或为空的源码账本会在不复制的情况下完成快照，标记会阻止后续分组变化变成同步。

两类快照不包含其他 `storages` 文件、home 级匿名用户标识、任何 `node_modules` 目录、临时 `.lock` 与 `.tmp` 写入文件和符号链接。因此，依赖安装不会把不同 Harness 版本耦合在一起，投影缓存不会跨版本流转，复制得到的链接也不会让桌面服务穿透到源码 home 进行读写。profile 仍属于配置，会在不带已安装依赖的情况下复制；外部 profile 插件必须另行安装到桌面端 home。会话附件与会话日志一起迁移，避免历史消息失去其引用的本地文件。

启动器先在目标目录同级的临时目录中构建每类快照。配置和历史发布会识别最大的缺失目标子树，再只发布这些根。工作区发布会排他创建缺失账本，或只原子替换再次验证为空的账本；若标记写入失败，则恢复原空账本。并发创建、非空或无法识别的目标状态会得到保留。迁移失败会回滚其已发布条目、报告错误，并且不会使用不完整快照启动服务。整个过程只读源码 home。`server.log` 会记录每次完成或跳过的原因及聚合复制数量，但不会写入配置名或配置值。

## 考虑过的替代方案

**复制完整的源码 home。** 这种方案最接近克隆，但还会复制可变存储状态、匿名身份、临时写入残留和绑定具体版本的依赖安装，违背桌面端 home 的隔离目的。

**持续同步两套 home。** 同步能让后续修改更方便，但会破坏独立的配置所有权，还会给可能运行不同版本的安装引入冲突和降级行为。

**只复制固定文件名列表。** 小型白名单容易审计，但会悄悄丢弃用户自建的 profile、preset、skill 和未来的配置类型。排除已知的非历史运行数据与安装产物，可以保留配置和对话，同时不把 home 中的所有可变条目都当作可迁移内容。

**从导入的会话 header 重建工作区。** header 的 cwd 可以重建目录分组，却无法恢复工作区 id、显示标题、工作区顺序、手动会话顺序和归档会话状态。导入兼容账本能够保留完整的分组账目，同时继续隔离无关存储状态。

## 后果

首次使用桌面端会继承缺失的源码配置、对话历史和兼容的工作区分组，但不会在两套 home 之间建立持续关系。配置与历史迁移会修复含有生成配置、但缺少对应版本标记或历史数据的桌面 home；独立的工作区迁移即使在前一类迁移已经完成时，也会修复已初始化的空分组账本。迁移时，桌面端 Harness 版本必须接受复制的磁盘格式；完成这些快照后，两套 home 可以分化到不同版本。清空全部桌面端配置后，下次启动会再次满足对应迁移条件。已有桌面端路径、历史、非空分组、归档状态和无关存储会得到保留。依赖符号链接或已安装外部 profile 包的源码配置，需要在桌面端显式提供对应替代项。

## 测试

桌面端单元测试覆盖配置、会话与附件复制，递归只补缺失目录，排除的条目类别，在启动器已生成配置旁导入历史，保护已有路径和历史，失败回滚，标记控制的一次性行为与空配置重新进入，诊断日志，以及显式 `DSH_HOME` 绕过。工作区用例覆盖目标账本缺失、home 迁移完成后修复经验证的空账本、保护非空账本、拒绝未知版本、排除投影缓存、禁止后续同步，以及标记发布失败时精确恢复原账本。所有 fixture 都使用临时 home，绝不检查或修改用户真实的 `~/.dsh` 或桌面端数据。
