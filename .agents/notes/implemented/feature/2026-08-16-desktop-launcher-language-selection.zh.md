# Agent Note: 桌面启动器语言选择

Status: implemented

[English](2026-08-16-desktop-launcher-language-selection.md) | 中文

## 问题

桌面启动器是在浏览器工作台打开之前显示的用户界面，但状态、操作和诊断中的中文常量会让英文系统以中文启动。浏览器工作台拥有独立的 locale 服务，无法翻译另一个 Python/Tk 启动器。

## 决策

启动器为固定标签、生命周期状态、操作和自有诊断提供完整的简体中文与英文字典。UI 绑定保留文案键和插值参数，因此切换活动语言无需重启受管服务，即可重新渲染当前的启动、就绪、更新或失败状态。外部异常详情在提供其上下文的已翻译诊断中保持原文。

有效的 `~/.dsh-desktop/language` 值是显式启动器偏好。没有该值时，macOS 读取有序的 `AppleLanguages` 偏好，Windows 读取用户有序的首选界面语言，其他平台读取标准 locale 环境值。解析过程从有序列表中选择第一个已提供的主语言；`zh` 与 `en` 都不存在时回退为中文。侧栏菜单立即切换语言，并通过原子替换保存 `zh` 或 `en`。

启动器偏好与 Harness home 中 Web UI 的 `locale.preference` 相互独立。两个程序运行于不同的 UI 进程，修改一方不会隐式改写另一方。

运行时部署抛出 `LocalizedError` 值，服务管理器返回延迟渲染的 `LocalizedText` 诊断。后台工作因此不依赖启动时的活动语言，屏幕上已经显示的失败也可以跟随之后的语言切换。

## 备选方案

**每次启动都跟随系统且不提供选择器。** 这能修复英文首次启动，但双语用户无法在产品内覆盖语言，操作系统语言顺序变化时还会丢失显式选择。

**复用 Web UI 偏好。** 这会让启动器依赖由其负责启动的服务所拥有的设置文档；服务就绪前的失败无法可靠地读取或修改该偏好。

**只翻译正常启动路径。** 英文用户在安装、更新、浏览器、迁移和服务失败时仍会看到中文，而这些状态最需要清晰指引。

**切换语言后重建窗口。** 销毁并重新创建 Tk 控件可能中断运行中 worker 周围的视觉状态。带键绑定更新现有控件，并保留服务所有权与进度。

## 后果

桌面 home 在 Harness 服务 home 之外增加一个不含敏感信息的 `language` 文件。macOS 系统语言检测会执行一次有时间限制且不经过 shell 的 `defaults` 读取；Windows 使用原生首选界面语言 API；其他平台依赖进程 locale 环境。产品名、已安装浏览器名、URL、版本和第三方原始异常详情有意不翻译。

## 测试

桌面单元测试验证有序主语言匹配、中英文系统偏好、显式选择优先级、无效已保存值的回退、原子持久化校验、macOS 偏好解析、字典键一致性，以及双语状态和错误渲染。现有启动器生命周期测试继续覆盖运行时、服务、浏览器和数据导入行为。
