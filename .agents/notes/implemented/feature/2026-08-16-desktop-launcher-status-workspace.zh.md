# Agent Note: 桌面启动器状态工作区

Status: implemented

[English](2026-08-16-desktop-launcher-status-workspace.md) | 中文

## 问题

桌面启动器需要在一个小型跨平台 Tk 窗口中表达环境准备、服务启动、就绪、失败和更新可用状态。居中的连续标签无法清楚表达这些状态之间的关系，也浪费了大部分窗口空间；依赖位图的按钮还会在不同显示缩放下产生较差的渲染效果。

## 决策

启动器采用固定的双栏工作区。左侧栏承载产品标识、两个启动阶段，以及桌面端和 Harness 版本；右侧用清晰标题表达当前状态，并以一个带边框的服务卡片持续展示进度、本地地址、运行时长和更新可用状态。每次运行状态切换都会同步更新标题、说明、阶段样式、状态标签、卡片详情和主操作。

启动器首先使用官方默认地址启动。当该次尝试报告 `EADDRINUSE` 时，启动器才使用官方 `--port 0` 参数重试一次，让操作系统选择可用的回环端口。服务的官方 `dsh web: <URL>` 输出是启动器的就绪信号和唯一地址来源。输出读取器把每一行同时写入 `server.log`，从该行提取规范 HTTP 或 HTTPS 地址，并传给状态卡和浏览器操作。其他进程退出情况或 60 秒内没有输出就绪行会使启动器停止子进程并报告失败；桌面壳绝不使用自行设定的 host 或端口作为回退。

唯一主操作在服务就绪后打开 Web UI，在失败后执行重试。原生主题按钮替代位图控件，使禁用、悬停和高分屏渲染在 macOS 与 Windows 上保持一致。关闭窗口仍然是明确的服务生命周期终止信号。

启动器会在启动时发现常见的已安装浏览器。仅检测到一款时，主操作保持为单一按钮；检测到多款时，按钮旁增加紧凑菜单，并在主操作中显示所选浏览器名称。切换选择只影响浏览器，地址仍然是服务发布的原始值。指定浏览器启动时会把该地址作为独立进程参数传入，不经过 shell。仅在没有识别到浏览器时，才以系统默认浏览器作为唯一回退。

## 备选方案

**保留居中的状态界面。** 这种方案实现最少，但无法建立稳定的信息层级，进度、版本、状态和操作在视觉上仍然彼此割裂。

**改用浏览器或原生框架。** 新的 UI 运行时会增加打包和生命周期工作，却无法改善启动器有限的交互模型。Tkinter 已经能够实现所需的卡片、状态样式和原生控件。

**保留基于图片的圆角按钮。** 预渲染图片能在单一缩放比例下提供精确圆角，但在高分屏上会出现明显边框和模糊像素，也无法自然适配禁用或悬停状态。

**显示当前默认地址。** 由桌面端持有 `127.0.0.1:3080` 实现更简单，但当官方运行器调整默认值时会发生漂移，端口被占用时也无法启动，还可能把占用该地址的其他进程错误识别为就绪服务。

**始终使用系统默认浏览器。** 这种方案无需发现浏览器，但无法让安装了多款浏览器的用户选择用于打开本地工作区的浏览器。

## 后果

窗口比原来的状态面板更宽，但无需打开其他视图即可读懂当前状态。启动中和就绪状态共用稳定布局，避免元素在无关位置之间跳动。视觉系统有意保持精简，仅依赖随包提供的标志图片和 Tk 主题控件。地址发现依赖官方就绪行保持稳定；缺失或格式错误的输出会明确失败，而不会打开猜测的端点。浏览器发现采用各平台维护的常见应用列表，且不会在多次启动之间持久化所选浏览器。

## 测试

桌面单元测试覆盖运行时长展示、默认端口后空闲端口的命令选择、端口占用分类、带动态端口和 LAN 后缀的地址解析、无关或不安全输出拒绝、日志同步写入、服务行为、浏览器发现、系统默认回退、无 shell 参数分隔和自有子进程终止。[运行时部署决策](../bug-fix/2026-08-16-desktop-runtime-deployment-reliability.md#testing)负责隔离的首次安装真实进程 smoke。打包 CI 会运行源码测试和每个冻结启动器的无界面配置检查。启动中、就绪、多浏览器和单浏览器 GUI 渲染仍依赖人工检查打包启动器。
