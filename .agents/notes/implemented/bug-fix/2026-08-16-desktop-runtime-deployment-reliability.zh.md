# Agent Note: 桌面运行时部署可靠性

Status: implemented

[English](2026-08-16-desktop-runtime-deployment-reliability.md) | 中文

## 问题

桌面启动器必须先准备 Node.js 与 `@deepseek-ai/dsh`，才能启动本地服务；这一步也需要适应 Node 或 npm 官方端点缓慢、不可达的网络。原实现会把浮动 npm 目标直接传给安装命令，在没有独立摘要的情况下信任下载归档，在 Windows 上使用 POSIX npm 路径，允许网络与 npm 工作在窗口关闭后继续运行，还会在更新成功前删除活动依赖树。只检查文件是否存在、把版本不相等当成更新，以及只构建不测试的发布工作流，都可能在没有覆盖这些失败模式时报告就绪或发布安装包。

## 决策

每个桌面版本固定一个精确 Node 版本和所有支持平台 Node 归档的 SHA-256。首次安装 Harness 时，会并发查询已配置注册表中的有效 `latest` 元数据，选择最高的 SemVer，并将该值冻结为本次部署事务的精确目标。Node 传输默认使用官方发行端点与 npmmirror；npm 默认使用官方注册表与 npmmirror。显式单一源或有序复数源配置是权威值，会禁用这些公共默认值。HTTP 操作有空闲超时，完整 Node 传输与 npm 安装分别有总时限，Node 部分下载与 npm 内容缓存可跨重试保留，注册表探测会优先选择能够证明所选精确包版本可达的源。代理与证书变量会传入 npm；环境中的 API key、密码、token、用户 home 和用户 npm 配置不会传入。

启动器先根据固定 SHA-256 验证 Node 归档，再验证所有归档成员路径并解压。平台特定 npm 定位在 POSIX 上使用 `lib/node_modules/npm`，在 Windows 上使用 `node_modules/npm`。Node 与 Harness 会安装到唯一的同级 staging 目录。发布前，Node `--version`、Harness 包 manifest 和已安装的 `dsh --version` 必须与固定或选定的精确版本一致。跨进程锁会串行化写入方；版本标记通过原子文件替换写入。

部署会报告写入锁获取、已安装运行时验证、版本解析、Node 传输与校验、注册表选择、Harness 安装与验证、切换和服务启动等具名活动。UI 只为 Node 传输显示根据字节数计算的百分比。没有可信总量的活动保留不确定进度条，同时显示精确目标、相关场景下选定的源，以及每秒更新的已用时间；事件队列保证 Tk 变更只在主线程执行。

更新绝不修改活动 Harness 目录。发布会保留原 Node 与 Harness 目录，只有 staging 验证通过后才切换；Harness 阶段、发布或发布后验证失败时会恢复完整的原目录组合及版本标记。启动时会恢复中断的重命名；只有可执行验证通过后才修复缺失标记；进程在两个组件发布之间停止时，会从活动目录和前一目录中选择一组有效组合。每次部署由一个 `DeploymentController` 拥有其子进程与进程组；关闭窗口会取消部署、等待进程结束、在需要时升级终止强度，并阻止同一启动器并发启动另一个 worker。

更新发现会并发查询已配置的注册表，选择最高的有效 SemVer 结果，并且只在它严格高于已安装版本时提示。更新操作会把这个精确版本传给部署，不会再次解析 `latest`。

## 考虑过的替代方案

**在每个桌面安装包中捆绑完整运行时。** 这会消除首次启动的网络依赖，但会在三个平台包中重复大型原生依赖树，并让每次 Harness 更新都依赖新的桌面版本。轻量启动器保留有界多源安装与持久缓存；如果实测区域失败率足以抵消发布和存储成本，离线包仍可作为独立分发选项。

**把 Harness 固定到桌面版本。** 固定包便于演练，但在桌面与 npm 的发布时间不一致时可能落后于注册表，甚至变得不可部署。先解析 `latest`，再把返回的精确版本冻结在一个事务中，可以安装当前版本，同时避免 npm 在探测、重试、验证或发布期间再次解析。Node 仍然固定，因为原生平台归档需要发版时确定的哈希。

**在活动目录中重试安装。** 复用单一目录占用更少磁盘，但超时、取消或镜像失败会破坏最后一份有效版本。staging 加一个保留的前一目录以磁盘换取回滚能力。

**只信任 HTTPS 传输，不使用发布摘要。** TLS 验证的是选定镜像的身份，而不是它提供的内容是否等于本仓库审查过的 Node 发布。固定 SHA-256 允许多个传输源提供同一份可进入安装的字节。

## 测试

- 运行时单元测试覆盖 SemVer 排序、权威源配置、并发注册表优先级、有界取消、敏感环境清理、部署锁、校验和拒绝、镜像回退、部分下载续传、归档路径穿越拒绝、可执行就绪检查、单组件与双组件中断发布恢复，以及失败更新的成对回滚。
- 活动测试覆盖每个阻塞部署阶段，并要求中英文文案同时包含所选 Harness 版本、经过清理的源和已用时间。
- 本地 HTTP fixture 提供一份符合当前平台目录结构的合成 Node 归档。真实部署控制器通过真实下载器取得它，执行归档中对应平台的 npm 入口，安装合成的精确 Harness 包，完成发布并验证其 CLI；整个过程不接触公共网络或用户数据。
- desktop 工作流会在 macOS arm64、macOS x64 和 Windows x64 打包前运行完整测试，然后针对隔离的临时桌面 home，通过 `--check` 执行每个冻结启动器。
- 打包前，每个平台任务都会要求两个默认 Node manifest 列出对应平台的固定归档及 SHA-256，并要求两个 npm 注册表都提供有效的 Harness `latest` 元数据。

## 后果

除非已经存在验证通过的缓存，首次安装仍需要至少一个已配置的 Node 传输源和 npm 注册表。Node 下载开始前还必须取得有效的 `latest` 元数据；失败会明确报错，而不是静默部署过时的后备版本。npm 不提供依赖解析与解压的稳定完成总量，因此其活动保留不确定状态，同时通过变化的阶段和已用时间区分正在工作与窗口冻结。维护者必须同时更新 Node 版本及所有平台哈希，Harness 发布则可以独立于桌面版本推进。缓存与一个前一版本运行时会占用额外磁盘；每次事务的精确选择、可恢复传输、有界关闭、Windows 一致性与回滚则可防止瞬时网络或进程失败替换最后一份有效运行时。
